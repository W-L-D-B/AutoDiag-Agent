# AutoDiag 前两周交付计划与验收标准

状态：已实现并通过本地质检；远端 CI 在推送后执行
修订：1
日期：2026-11-06

## 目标

在纯软件环境中交付一个可复现的车载通信台架：三个独立 C++ ECU 进程经 Linux `vcan0` 周期发布状态和心跳，C++ 监视器验证协议并形成快照与逐帧证据，Python 场景编排器可以稳定复现正常与故障场景。

## 范围

本阶段包含：

- 固化 v1 CAN/DBC、LIN 软件模型、故障场景和 JSON 证据格式。
- BMS、HVAC、Body 三类 C++ ECU 节点；同一可执行文件使用 `--node` 选择节点。
- 独立 C++ 监视器，负责 CRC、序号、在线状态与数据新鲜度判定。
- 正常、丢数据、坏 CRC、冻结序号、BMS 过温、LIN 坏校验和、节点退出等确定性场景。
- 场景编排、逐帧日志、最终快照、离线回放和 DBC 交叉校验。
- 单元测试、真实 `vcan0` 集成测试、ASan/UBSan、覆盖率、CI 和中文运行教程。

本阶段不包含 UDS 服务、Unix Domain Socket/TCP 业务服务、Android 应用、AIDL/VHAL、LLM/MCP Agent 和真实 CAN/LIN 硬件。这些属于后续里程碑。

## 工作流边界

```text
run_bench.py
  ├─ 启动 autodiag-monitor，等待 ready=true
  ├─ 分别启动 3 个 autodiag-ecu 进程
  ├─ 监督退出状态并写 manifest.json
  └─ 得到 frames.jsonl + snapshot.json

autodiag-ecu ──SocketCAN/vcan0──> autodiag-monitor
       │                                  │
       └─ HVAC 内部 LIN 软件模型          └─ CRC/序号/新鲜度/在线判定

frames.jsonl ──replay_log.py──> replay.json
```

监视器必须先成功绑定 CAN 接口并以原子替换方式写出 `capture_state="listening", ready=true`，编排器才能启动 ECU。退出时监视器原子写出 `capture_state="completed", ready=false`。测试不得依赖固定时长 `sleep` 来猜测监视器是否就绪。

## 不变量和风险边界

1. 每种 CAN 帧固定为 8 字节、小端编码；所有保留位必须为零。
2. 数据帧周期为 100 ms，心跳周期为 250 ms。周期是软件调度目标，不宣称硬实时；验收只检查有界数量与时间窗口。
3. 数据在最后一个已接受帧之后 500 ms 变为 stale；节点在线只取决于最后一个已接受心跳是否小于 1200 ms。两者互相独立。
4. CRC 错误帧、重复帧和旧序号帧不得刷新数据或心跳时间，不得改变已解码信号。逐帧证据必须同时保存带 CAN flags 的原始 ID、仲裁 ID、DLC 和 payload，使离线回放能独立复验帧类型与长度。
5. 数据序号按 8 位模运算：首次有效帧建立基线；差值 1..127 为前向帧；0 永远是重复；128..255 为旧帧。
6. 数据 stale 本身不得重置序号基线。仅当有效心跳表明节点 epoch 改变时重置数据基线：心跳 uptime 回退，或心跳已经 offline 后重新出现。epoch 改变时清除旧数据值、接受时间和 counter，使状态回到 missing；这样既不显示上次启动的值，也不会让冻结序号故障每 500 ms 被误恢复。
7. v1 只有 8 位序号，在线节点在长时间数据缺口中若前进超过半窗口会产生歧义；本版本选择拒绝这些帧直到节点 epoch 改变。这是已知限制，不是安全或量产保证。
8. HVAC 的 LIN 是进程内协议模型，不接触串口、收发器或电气层。坏 LIN 校验和时保留 last-good 温度并清除 CAN `cabin_valid` 位。
9. 故障注入只允许作用于 `vcan*`。代码和脚本必须拒绝在非虚拟 CAN 接口上发送测试帧。
10. 日志使用相对监视器启动时刻的单调时钟；不把墙钟时间用于帧排序或超时判定。
11. SIGINT/SIGTERM 应使进程停止并冲刷/关闭输出；场景编排器必须回收所有子进程。`exit` 故障的预期退出码固定为 42，参数错误为 2。
12. 未经真实 ECU、CAN/LIN 收发器、总线负载和故障注入台架验证，不得声称具备硬实时、电气正确性、EMC、功能安全或量产能力。

## 验收标准

### AC-001：协议契约可被两套实现读取

- 场景：v1 DBC 和协议文档存在。
- 操作：加载 DBC，并用 C++ 编解码与 Python `cantools` 处理同一组已知向量。
- 期望：CAN ID、字节序、缩放、单位和字段值完全一致；CRC/LIN 已知向量通过。
- 验证：C++ 单元测试和 Python 协议测试。

### AC-002：三个进程发布独立状态

- 场景：`vcan0` 已启动、监视器已 ready。
- 操作：分别启动 BMS、HVAC、Body ECU 3 秒。
- 期望：监视器收到每个节点的数据帧与心跳；最终三个节点均 online，数据均 fresh，信号落在文档范围内。
- 不得：一个进程模拟三个节点，或用日志文件代替真实 SocketCAN 收发。
- 验证：真实 `vcan0` 集成测试和基线演示。

### AC-003：有效性与序号判定可复现

- 场景：输入有效、坏 CRC、重复、旧序号、255→0 回绕及节点重启序列。
- 操作：交给监视器状态机。
- 期望：仅有效前向帧更新信号；回绕接受；坏 CRC/重复/旧帧按原因累计拒绝；epoch 改变后下一数据帧建立新基线。
- 验证：不使用真实时间的确定性单元测试。

### AC-004：故障互不混淆

- 场景：逐一运行七个固定场景。
- 操作：场景编排器按 manifest 配置启动节点。
- 期望：丢数据只使 BMS data stale、坏 CRC 累计 HVAC CRC 拒绝、冻结计数累计 Body duplicate 且保持 stale、过温仍是协议有效但温度为 125.0°C、坏 LIN 清除 `cabin_valid` 并保持 last-good、节点退出最终 offline。
- 验证：每个场景至少一个集成断言；相同 seed 和相同逻辑 tick 的纯模型输出一致。实时进程重跑应得到相同故障分类和匹配 data counter 的信号值，但不要求边界帧总数或 heartbeat uptime 完全相同。

### AC-005：证据可离线重放

- 场景：已有完整 `frames.jsonl`。
- 操作：运行 `replay_log.py`。
- 期望：重放结果的最终信号、计数器、拒绝计数和 resynchronizations 与在线快照一致；年龄字段可按日志尾部重算。
- 不得：回放读取场景真值或调用实时 CAN。
- 验证：基线和至少一个故障日志的回放集成测试。

### AC-006：构建和质量门禁通过

- 操作：运行 Debug、ASan/UBSan、测试、覆盖率、格式/静态检查和公开内容检查。
- 期望：所有门禁为绿色；测试没有残留进程；Git 工作树只含预期变更；无凭据、个人信息或生成日志被提交。
- 验证：本地验证报告和 GitHub Actions。

## 验证矩阵

| 验证层 | 必须覆盖 |
|---|---|
| 纯单元 | CRC8、LIN PID/增强校验和、字节编解码、序号回绕/重复/旧帧、epoch 重置、新鲜度 |
| DBC 交叉检查 | 三类数据帧的 C++ 编码与 `cantools` 解码一致 |
| 真实 vcan 集成 | 基线、每种故障、节点进程退出、日志写入、回放一致性 |
| 动态分析 | ASan + UBSan，无内存错误和未定义行为 |
| 静态/风格 | 编译警告视为错误、clang-format、clang-tidy 或等价检查、Ruff |
| 可复现性 | 纯模型固定 seed/tick 输出一致；实时重跑的故障分类和匹配 data counter 信号一致；同一日志回放完全一致 |
