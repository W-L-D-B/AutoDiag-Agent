# 第二阶段：从 CAN 广播到诊断服务

## 先理解这次增加的能力

ECU 是电子控制单元，在本项目里是一个独立 Linux 进程。BMS、HVAC、Body 每隔一段时间广播数据，相当于不断报数。广播数据适合观察状态，但不能回答“请现在读取 BMS 温度”这样的请求。

诊断协议补上主动问答能力。UDS 定义“问什么、怎样回答”，ISO-TP 负责把较长问答拆成 CAN 帧并重新组装。程序实际使用 Linux `CAN_ISOTP` 套接字，内核处理首帧、连续帧和流控，C++ 处理完整 UDS PDU。

## 从字节到含义

`22 D1 02` 中，`22` 是读取数据服务 SID，`D1 02` 是温度数据标识 DID。成功响应例如 `62 D1 02 40 01`：`62=22+40`，标识仍为 D102，数据 `40 01` 按本项目小端有符号数解释为 320，再乘 0.1 得到 32°C。DID 标识本身按大端编码，数据字节序由契约单独规定，不能混为一谈。

信号 DID 需要先发 `10 03` 进入扩展会话；闲置 5000 ms 会恢复默认会话。`7F 22 31` 是 ECU 明确回答“该读取不支持/当前不可用”，这叫 NRC 否定响应；没有收到回答叫传输超时。两者不能合并为温度 0°C。

F180 读取软件版本，响应超过 CAN 单帧有效载荷。集成测试实际捕获到 First Frame 和 Consecutive Frame，证明多帧链路确实经过了内核。

## 为什么还需要 C++ 服务

持续服务把六种周期报文更新到内存状态，并为每个节点保留最多 512 个已接受信号样本。调用 snapshot 得到实时快照，signal_window 得到有限历史。坏 CRC、重复序号、旧序号不会刷新样本时间。

每个结果都有服务启动命名空间、证据编号与单调时间。服务重启后编号空间改变，客户端不能把两个进程的相对时间直接相减，也不能把旧结果显示成当前值。

本机 Unix Domain Socket 用于 Linux 进程间通信，目录权限 0700、套接字 0600。独立 TCP 网关把相同接口提供给 Android。两端使用四字节大端长度加 UTF-8 JSON，因此即使 TCP 把消息切成半包或合并发送，接收方也能明确边界。长度、连接数、历史和事务时间都有上限。

## 用跨通路证据定位问题

`drop_bms_data` 中，BMS 心跳继续、广播数据变旧，但 DID 仍可读到内部当前温度。这支持“周期发布链路异常”，不能推出“ECU 已死机”。

`wrong_bms_scale` 中，广播电压约为 40 V，而诊断 DID 约为 400 V。两路数据使用同一内部模型却通过不同编码路径输出，对照可以定位缩放不一致。Agent 后续负责选择这些工具并组织证据，协议解析和数值换算仍由确定性代码完成。

`bms_overtemperature` 的 125°C 是传输有效的异常业务值。读取 DTC 得到 A10001；`lin_bad_checksum` 导致 HVAC 输入有效位清零及 A20001。DTC 来自实际模型条件，不读取注入场景名称。

## 并发与错误恢复

服务允许最多八个连接工作线程；同一 ECU 的诊断事务串行，防止会话切换与回复交错。不同 ECU 可以分别诊断。

UDS 没有通用请求编号。请求 A 超时后，即使请求 B 使用同一 DID，也无法判断随后到达的响应属于 A 还是 B。本项目选择明确隔离该 ECU 诊断通道并要求整栈重启恢复，避免给旧数据盖上新证据编号。周期状态和其他 ECU 仍可读取。

## 自己动手理解

按 README 启动持续台架，先读 snapshot，再读 D102 与 DTC。随后停止台架，以 `--scenario drop_bms_data` 重启，观察 online=true/data_status=stale，再比较 DID。最后以 `--scenario wrong_bms_scale` 比较广播电压与 D100（53504）。这些操作使用同一份真实 C++ 服务和虚拟总线。

面试时可以按“问题—设计—证据—边界”讲：多进程周期通信需要主动诊断与可关联结果；用原生 ISO-TP、UDS 会话、持续采集、Unix RPC/TCP 分层实现；通过多帧、并发、故障和退出测试验证；当前是软件台架与 UDS 子集，不声称完整 AUTOSAR、物理 LIN 或量产诊断认证。
