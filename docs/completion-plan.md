# AutoDiag-Agent 完整交付计划

基线：`536bffe`。本计划承接已经完成的虚拟 ECU 台架，并依据用户对“完成项目、质检通过后同步 GitHub”的授权继续实现。文档定义验收目标，不预先宣称尚未执行的测试已通过。

## 交付边界

最终软件闭环为：用户在 Android 或本机提交诊断问题，Agent 调用受约束工具，经 C++ 服务读取真实虚拟总线、ISO-TP/UDS 响应与历史样本，提出并验证故障假设，生成带证据的报告。

全部车辆操作限制在 `vcan` 软件台架。项目不声称通过实车电气、完整 AUTOSAR、功能安全或 OEM 诊断一致性认证。应用级 AIDL/Binder 与系统 VHAL 分开描述。模型规划不能替代协议解析、数值计算和测试判定。

## 里程碑

| 里程碑 | 实际交付 | 必须验收 |
|---|---|---|
| M1：已有台架 | 三个 C++ ECU、CAN/DBC、LIN 模型、监视器、故障复现与回放 | 保留基线测试和原有协议行为 |
| M2：车端诊断与服务 | ECU 原生 `CAN_ISOTP` UDS 子集，持续采集服务，Unix RPC 与独立 TCP 网关 | 真实多帧响应、会话超时、NRC、离线/超时、并发隔离、协议分帧边界与安全退出 |
| M3：Android 客户端 | Java Activity，独立 `:gateway` 进程 AIDL 服务，后台网络调用，状态与证据页面 | APK 可复现构建、模拟器安装、Binder 跨进程、正常和失败流程、重新绑定与连接恢复 |
| M4：诊断 Agent | 工具注册/MCP、真实模型适配器、诊断循环、检查点、HTTP 任务服务、受限文档检索 | 实际工具结果驱动推理；错误/预算/取消/恢复可观察；不泄漏故障真值或 API key |
| M5：评测与交付 | 固定 60 个诊断任务、规则基线、真实模型演示、质量报告和教学文档 | 公布任务构成、划分与实际成绩，最终完整演示，质检后提交和推送 |

每个里程碑以可运行版本推进，先验证再提交。后续修改必须保留已有正常路径和回归测试；协议变化先更新对应版本文档。

## M2 约束

- 所有数据和诊断 CAN ID、时间阈值与 UDS 字节编码由 [diagnostics-v1.md](diagnostics-v1.md) 和 [service-api-v1.md](service-api-v1.md) 固定。
- ECU 的诊断值来自内部当前信号模型。周期 CAN 丢包或应用 CRC 故障不能直接破坏诊断通路，也不能让 ECU 通过额外字段泄漏注入器场景名。
- Live collector 只订阅原六个周期 CAN ID，避免把 ISO-TP 诊断帧计入周期信号拒绝计数。旧离线监视器仍可把诊断 ID 记录为未知 ID；它不是总线物理错误判断器。
- 时间使用服务进程的单调时钟；服务重启改变证据命名空间。不同操作系统的时钟不能直接相减。
- 有界连接、请求长度、历史样本和事务期限；停止时关闭并回收自己创建的线程、套接字与子进程。

## M3 约束

- Activity 只负责交互和呈现。AIDL 服务声明独立 `:gateway` 进程，且不对其他应用导出。
- UI 主线程不执行网络等待。Binder 调用和回调应有请求 ID 关联，断开后呈现明确状态，恢复时重新绑定。
- 模拟器通过 `10.0.2.2` 访问 Windows localhost 转发至 WSL 的本地网关。无认证开发接口只绑定本机回环地址。
- 使用已安装 SDK 的 `aidl/javac/d8/aapt2/zipalign/apksigner` 构建；项目不依赖为演示额外引入 Maven/AndroidX。
- 页面区分数据 stale、ECU offline、诊断 NRC 和连接失败；旧值及无效传感器输入不能显示成正常实时值。

## M4 约束

- 模型提供商适配器支持本地 Ollama 或兼容的模型 HTTP API；端点、模型名和凭据由未跟踪的本地配置提供。
- 工具白名单映射到固定 RPC 方法，不提供任意 shell、任意文件读取或不受限制的 URL 调用。工具参数使用结构化校验。
- 文档检索只读取项目允许目录中的公开接口与操作说明。实时数值从结构化工具获取，不能从向量检索片段猜测。
- 工具响应与生成报告携带真实 `evidence_id` 和时间来源。模型编造的证据 ID 不能通过最终报告验证。
- 检查点保存任务状态、步骤、工具结果和预算，不保存 API key。恢复后重新确认服务 boot namespace，旧证据不当作当前实时状态。
- 任务有步数、工具调用、单工具时间及总时间预算；支持取消、失败、数据不足与继续取证，不把工具失败包装成诊断成功。
- mock/replay 模式用于确定性工程测试。真实模型验收和评测必须独立标记，不能用回放成绩冒充真实推理成绩。

## M5 评测规则

60 个任务应由预先定义的场景族和参数变体组成，明确区分车辆故障、通信/服务故障与数据不足案例。不能仅把相同问题改写 60 次后宣称覆盖 60 种故障。若最终场景构成与早期研究建议不同，报告按实际构成写明。

故障真值由独立评测器保管。Agent 的工具、文档检索和检查点不能读取 `manifest.json`、场景名到根因的映射或答案文件。留出任务在冻结后执行；同一任务集用于规则基线和真实模型对比。

指标至少包含任务完成、根因定位、有效证据、无依据结论、调用数、耗时及 token/成本（可获得时）。正常/异常路径均须能复现；模型效果、工程链路正确性和外部服务可用性分别报告。

## 总体验收矩阵

| 编号 | 触发与预期 | 证据 |
|---|---|---|
| AC-01 | 保持已有台架正常、故障、回放和退出行为 | 旧单元/契约/集成测试仍通过 |
| AC-02 | 请求 F180 得到超过单帧的真实 UDS 响应；默认会话拒绝信号 DID；扩展会话可读；S3 到期回默认 | Fake-clock 单元测试与原生 ISO-TP 集成测试 |
| AC-03 | 半包、粘包、错误长度/JSON/参数、断开和超时均有边界行为；并发诊断不串回复 | Framed RPC/TCP 与并发集成测试 |
| AC-04 | 周期数据停止但心跳继续时，live snapshot 呈 online/stale；诊断通路仍可取当前模型值 | 服务层跨通路故障测试 |
| AC-05 | Android 在模拟器中显示实时/失效状态，AIDL 服务确实在独立进程，UI 不被请求等待阻塞 | 安装、进程、操作流程和实际响应证据 |
| AC-06 | Agent 在真实模型模式选择工具、验证假设并输出可核验报告；工具超时、取消和重启恢复行为明确 | 固定端到端任务及检查点验证 |
| AC-07 | 60 个任务隔离真值，模型与规则成绩按实测给出 | 冻结任务集、运行记录、汇总报告 |
| AC-08 | 质检通过后同步明确提交至 GitHub；凭据和个人资料不发布 | 测试/静态分析/覆盖率结果、发布检查与远端 SHA |
